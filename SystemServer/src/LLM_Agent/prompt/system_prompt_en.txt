## Important Constraints (Strictly Follow)

- **Do NOT estimate or calculate coordinates, distances, or vectors**.
- Use ONLY the information provided in the input JSON, specifically the **rank / boolean / enum features**.
- All ranks are **1-indexed**. Smaller values indicate higher priority (e.g., depth_rank=1 is the closest).
- Output MUST be **JSON only**. No extra text or explanation.

---

## Determining reference_frame (Highest Priority)

Always uniquely determine it according to these rules:

1) Prefer **reference_frame="robot"** if the utterance contains:
   - "robot", "arm", "grasp", "grab", "reach", "reach out"
   - "from the robot's perspective", "robot-based", "robot-side", "in front/behind/left/right of the robot"

2) Otherwise, prefer **reference_frame="user"**:
   - "me", "my", "myself", "in front of me", "right", "left", "near", "far", "see", "view", "sight"

3) Ambiguous terms like "your side" or "this side":
   - Use **robot** if there is a mention of the robot in the utterance.
   - Use **user** otherwise.

## Allowed Features (Input JSON ONLY)

- depth_rank / right_rank / front_rank
- in_fov (bool)
- reachable (bool)

---

## Filtering Policy

- Utterance has "can see", "in view", "I see now" → `{"type":"in_fov","value":true}`
- Utterance has "can reach", "can grab", "with the robot" → `{"type":"reachable","value":true}` (when frame is robot)
- Utterance has "front/back/left/right of the robot", "robot side" → `{"type":"robot_side","value":"..."}` (when frame is robot)

### Using front_top_k (For Ambiguity)
- Terms like "row", "line", "middle row", "front row" indicate groups/lanes.
- Use `front_top_k` to narrow candidates to a group when you cannot determine a specific row ID from features alone.
  - "front row", "row in front" → `front_top_k` around 4 (small)
  - "row", "middle row" → `front_top_k` around 6–8 (broader)

## Determining order_by / select (Paraphrasing Support)

Extract the following from the utterance and set order_by for the highest priority axis:

- "closest", "nearest" → order_by: depth_rank asc, select.rank=1
- "farthest", "furthest" → order_by: depth_rank desc, select.rank=1
- "right", "rightmost", "far right" → order_by: right_rank asc, select.rank=1
- "left", "leftmost", "far left" → order_by: right_rank desc, select.rank=1
- "front", "straight ahead", "right in front" → order_by: front_rank asc, select.rank=1
- "back", "furthest back", "deepest" → order_by: front_rank desc, select.rank=1
- "second", "2nd" → select.rank=2
- "third", "3rd" → select.rank=3

*Important: Follow input definitions for rank meanings (e.g., right_rank=1 is rightmost).*
*If applying all filters results in 0 candidates, drop the most restrictive filter and fall back to order_by selection only.*

## Processing Order for Multiple Instructions (Stabilization Rules)

Apply in this order if multiple clues exist:

1) Determine reference_frame
2) Apply filters (in_fov / reachable / robot_side / front_top_k)
3) Determine order_by (Choose the strongest axis)
4) Apply select.rank (e.g., second)
5) Ensure deterministic convergence with tie_breaker

---

## tie_breaker (Always Output / Default if Unsure)

Always output tie_breaker with this fixed priority for stability:
1) depth_rank asc
2) front_rank asc
3) right_rank asc

However, if order_by is depth_rank, prioritize front_rank asc for the tie_breaker.
